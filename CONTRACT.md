# Контракт API

Написан **до** кода. Это эталон: если код ведёт себя иначе — дефект в коде,
а не повод переписать этот файл. Правки контракта — отдельным решением человека,
с записью в журнал.

Базовый адрес: `http://localhost:3000`. Все тела — JSON в UTF-8.

## Объект заметки

```json
{
  "id": "8f0c3f7e-8b2a-4c1d-9b3e-2a5f6d7c8e90",
  "title": "Купить молоко",
  "text": "И хлеб тоже",
  "tags": ["дом", "покупки"],
  "createdAt": "2026-08-14T09:41:12.334Z",
  "updatedAt": "2026-08-14T09:41:12.334Z"
}
```

| Поле | Тип | Правила |
|---|---|---|
| `id` | string | UUID v4, генерирует сервер. Клиент прислать не может |
| `title` | string | Обязательное при создании. После `trim` — от 1 до 200 символов |
| `text` | string | Необязательное, по умолчанию `""`. До 10 000 символов |
| `tags` | string[] | Необязательное, по умолчанию `[]`. До 20 тегов, каждый после нормализации от 1 до 32 символов |
| `createdAt` | string | ISO 8601, UTC. Ставит сервер, не меняется |
| `updatedAt` | string | ISO 8601, UTC. Обновляется при каждом изменении |

### Нормализация тегов

Применяется и при сохранении, и к параметру фильтра `tags`:

1. `trim` по краям;
2. приведение к нижнему регистру;
3. выброс пустых строк;
4. схлопывание дублей с сохранением порядка первого вхождения.

`["  Работа ", "работа", "РАБОТА", ""]` → `["работа"]`.

Нормализация происходит молча, но ответ всегда содержит итоговый список тегов,
поэтому изменение клиенту видно.

## Формат ошибки

Единый для всех кодов. Поле `field` присутствует только там, где ошибка
привязана к конкретному полю или параметру.

```json
{ "error": { "code": "validation_error", "message": "title: обязательное поле", "field": "title" } }
```

| Код HTTP | `error.code` | Когда |
|---|---|---|
| 400 | `invalid_json` | Тело не разбирается как JSON или это не объект |
| 400 | `validation_error` | Поле или query-параметр не проходит правила выше |
| 400 | `unknown_field` | В теле или в query-строке есть поле либо параметр, которого нет в схеме |
| 400 | `empty_patch` | `PATCH` без единого изменяемого поля |
| 404 | `not_found` | Неизвестный `id` или неизвестный маршрут |
| 405 | `method_not_allowed` | Метод не поддерживается на существующем пути. В ответе — заголовок `Allow` |
| 409 | `idempotency_key_conflict` | Тот же `Idempotency-Key` прислан с другим телом |
| 500 | `internal_error` | Непредвиденная ошибка. Наружу уходит только код и общая фраза |

Стектрейсы, пути к файлам и содержимое исключений наружу не отдаются никогда —
только в консоль сервера.

`Content-Type` запроса не проверяется: тело просто разбирается как JSON.
Отдельный `415` не вводим сознательно — лишний код ради редкого случая.

Тело запроса больше **1 МиБ** отклоняется на чтении, до разбора JSON:
`400` `validation_error`, `field: "body"`. Значение `body` в поле `field` —
единственное, которое не соответствует настоящему полю схемы.

## Приоритет ошибок

Когда в одном запросе не так сразу несколько вещей, порядок проверок такой:

1. Заголовок `Idempotency-Key` проверяется до того, как тело вообще прочитано.
2. Размер тела — до разбора JSON.
3. Разбор JSON — до валидации полей.
4. Неизвестное поле — до проверки обязательных: `{"titel": "x"}` даст
   `unknown_field`, а не «отсутствует title».
5. **Тело валидируется до проверки существования `{id}`.** Поэтому `PATCH`
   с пустым телом на несуществующий `id` вернёт `400` `empty_patch`, а не `404`.

## Эндпоинты

### `GET /notes` — список с фильтром

Параметры запроса:

| Параметр | По умолчанию | Правила | Нарушение |
|---|---|---|---|
| `tags` | нет фильтра | Список через запятую. Нормализуется как теги заметки. После нормализации список не должен быть пустым | `400` `validation_error`, `field: "tags"` |
| `limit` | `20` | Целое от 1 до 100 | `400` `validation_error`, `field: "limit"` |
| `offset` | `0` | Целое ≥ 0 и не больше `Number.MAX_SAFE_INTEGER` | `400` `validation_error`, `field: "offset"` |
| любой другой | — | Не допускается | `400` `unknown_field` с именем параметра |

Строгость к query-параметрам такая же, как к телу запроса: `?foo=bar` — это
`400`, а не «не заметим». Плата принята сознательно: ссылка с `?utm_source=`
на этот эндпоинт тоже получит `400`.

Повторённый параметр (`?limit=1&limit=2`) читается по первому значению.

Фильтр по тегам работает по **И**: заметка попадает в выборку, только если у неё
есть все перечисленные теги. Порядок — по `createdAt`, новые сверху.

`200`:

```json
{ "items": [ { "id": "…", "title": "…", "text": "…", "tags": [], "createdAt": "…", "updatedAt": "…" } ],
  "total": 42, "limit": 20, "offset": 0 }
```

`total` — число заметок, прошедших фильтр, а не общее число в хранилище.
`offset` больше `total` — это `200` и пустой `items`, а не ошибка.
Ничего не нашлось по фильтру — тоже `200` и пустой `items`.

### `POST /notes` — создать

Принимаемые поля: `title` (обязательное), `text`, `tags`. Любое другое поле —
`400` `unknown_field` с его именем в `field`. Прислать `id`, `createdAt` или
`updatedAt` нельзя: это тоже `unknown_field`.

```json
{ "title": "Купить молоко", "text": "И хлеб тоже", "tags": ["Дом", "покупки", "дом"] }
```

`201` — созданная заметка целиком, с нормализованными тегами.

**Идемпотентность.** Необязательный заголовок `Idempotency-Key`, строка от 1
до 128 символов:

| Ситуация | Ответ |
|---|---|
| Ключа нет | `201`, каждый запрос создаёт новую заметку |
| Ключ новый | `201`, заметка создаётся, пара «ключ → заметка» запоминается |
| Ключ известен, тело то же | `200` и **та же самая** заметка. Ничего не создаётся |
| Ключ известен, тело другое | `409` `idempotency_key_conflict` |
| Ключ известен, тело то же, но заметка уже удалена через `DELETE` | `201` и **новая** заметка с новым `id`. Ключ освобождается |
| Ключ пустой или длиннее 128 | `400` `validation_error`, `field: "Idempotency-Key"` |

«То же тело» определяется как совпадение SHA-256 сырого тела запроса.
Запись о ключе хранится в файле вместе с заметками и живёт 24 часа,
после чего вычищается при ближайшей записи.

### `GET /notes/{id}` — одна заметка

`200` — объект заметки. Неизвестный `id` — `404` `not_found`. Синтаксически
битый `id` (например, обрывок percent-кодирования `%zz`) — тоже `404`,
а не ошибка валидации: с точки зрения клиента такой заметки просто нет.

### `PATCH /notes/{id}` — изменить

Частичное изменение: присылаются только меняющиеся поля из `title`, `text`, `tags`.
Непереданные поля остаются как были.

| Ситуация | Ответ |
|---|---|
| Успех | `200` и заметка целиком, с обновлённым `updatedAt` |
| Пустое тело `{}` | `400` `empty_patch` |
| Неизвестное поле | `400` `unknown_field` |
| Значение не проходит правила | `400` `validation_error` с именем поля |
| Неизвестный `id` | `404` `not_found`. Запись по чужому id не создаётся |

`tags` заменяются целиком, а не дополняются: прислали `["дом"]` — стало `["дом"]`.

### `DELETE /notes/{id}` — удалить

`204` без тела. Неизвестный `id` — `404` `not_found`. Повторное удаление того же
`id` — тоже `404`: удаление не идемпотентно, и это осознанный выбор.

## Хранилище

Файл `data/notes.json`, структура:

```json
{ "version": 1, "notes": [], "idempotency": [] }
```

| Состояние файла | Поведение сервера |
|---|---|
| Файла нет | Создаётся при старте с пустой структурой |
| Файл пустой или состоит только из пробельных символов | Трактуется как пустая структура и переписывается корректной |
| Файл не разбирается как JSON или структура не та | Сервер **не стартует**: в консоли путь к файлу и причина. Данные не перезаписываются |

«Пустой» — это и ноль байт, и файл из одних пробелов или переводов строки:
данных в нём нет, терять нечего. Формулировка расширена сознательно, после
аудита: изначально контракт говорил «0 байт», код уже вёл себя шире, и решение
принято в пользу кода.

«Структура не та» — это в том числе отсутствующее или отличное от `1` поле
`version`, а не только `notes` и `idempotency` не тех типов.

Запись атомарная: временный файл в той же папке, затем переименование поверх
рабочего. Незавершённая запись не может оставить наполовину записанный JSON.
