# Сервис заметок с тегами

Мини-API из домашнего задания после занятия 1 (направление Backend).
HTTP-сервис для заметок с тегами: хранилище — один JSON-файл, базы данных нет,
внешних зависимостей нет вообще.

Задание выбрано из списка вариантов — «сервис заметок с тегами». Взял его
потому, что кода там мало, а неоднозначностей много: регистр тегов, дубли,
пустые строки, лишние пробелы. Именно эти места агент по умолчанию решает
молча и по-своему, а значит на них видно, работает ли связка «контракт → код →
независимая сверка».

## Что нужно для запуска

**Node.js 22.19.0** (или новее в пределах 22.x). Больше ничего:
`npm install` выполнять не нужно, зависимостей в проекте нет.

## Запуск

```bash
npm start
```

Сервис поднимется на `http://localhost:3000`. Порт меняется переменной
окружения `PORT`, путь к хранилищу — переменной `NOTES_FILE`.

Файл `data/notes.json` создаётся автоматически при первом запуске.

## Тесты

```bash
npm test
```

39 тестов: успешные сценарии, ошибки валидации, коды ответов, поведение
хранилища при отсутствующем, пустом и испорченном файле. Тесты не ходят в сеть
и не трогают рабочий `data/notes.json` — каждый работает со своим файлом
во временной папке ОС и убирает его за собой.

## Проверить руками

Файл [requests.http](requests.http) — 12 запросов с заранее записанными
ожидаемыми ответами: один успешный сценарий, ретрай и десять ошибочных.
Открывается плагином REST Client в VS Code.

Через curl (bash):

```bash
curl -s -X POST http://localhost:3000/notes -H "Content-Type: application/json" -H "Idempotency-Key: demo-1" -d '{"title":"Купить молоко","tags":["  Работа ","работа","РАБОТА",""]}'
```

В PowerShell так не сработает — кавычки внутри одинарных не экранируются и до
сервиса доезжает битый JSON (сервис честно отвечает `400 invalid_json`).
Рабочий вариант — положить тело в файл:

```bash
curl.exe -s -X POST http://localhost:3000/notes -H "Content-Type: application/json" --data-binary "@body.json"
```

## Что сделано

Пять эндпоинтов, полностью описанные в [CONTRACT.md](CONTRACT.md) **до** кода:

| Метод | Путь | Что делает |
|---|---|---|
| `GET` | `/notes` | Список с фильтром по тегам (по И), `limit`, `offset` |
| `POST` | `/notes` | Создать заметку, с необязательной идемпотентностью |
| `GET` | `/notes/{id}` | Одна заметка |
| `PATCH` | `/notes/{id}` | Частичное изменение |
| `DELETE` | `/notes/{id}` | Удалить |

- Валидация: обязательные поля, типы, длины строк, границы чисел, нормализация
  тегов, лимит на размер тела.
- Единый формат ошибки `{"error": {"code", "message", "field"}}`, коды
  400 / 404 / 405 / 409 / 500. Стектрейсы наружу не уходят.
- Идемпотентное создание по заголовку `Idempotency-Key`: повторный запрос с тем
  же ключом и тем же телом возвращает `200` и ту же заметку, с другим телом — `409`.
- Хранилище: атомарная запись через временный файл и переименование;
  отсутствующий и пустой файл создаются заново, испорченный **не** перезаписывается —
  сервис отказывается стартовать и говорит, какой файл и почему его не устроил.

## Чего не сделано — сознательно

- Нет базы данных, Docker и любых внешних сервисов — прямое условие задания.
- Нет внешних npm-зависимостей, включая dev: ни фреймворка, ни тест-раннера,
  ни линтера. Линтер и форматтер не подключены вообще.
- Нет аутентификации и пользователей: сервис однопользовательский.
- Нет поиска по тексту (`?q=`), сортировки по выбору клиента и фильтра «хотя бы
  один тег» (OR). Каждый такой параметр — своя валидация и свои тесты, а задание
  просит держать поверхность маленькой.
- Нет одновременной работы двух экземпляров сервиса над одним файлом.
  Хранилище целиком читается в память при старте, и второй процесс затрёт чужие
  изменения. Для учебного объёма это неважно, в реальном — первое, что сломается.
- Нет мягкого удаления: `DELETE` удаляет насовсем, повторный `DELETE` даёт `404`.

## Принятые допущения

Полный список с обоснованиями — в [SPEC.md](SPEC.md), здесь коротко:

- **Теги нормализуются молча** (`trim`, нижний регистр, без дублей и пустых),
  но ответ всегда возвращает итоговый список — клиенту видно, что сервер изменил.
- **Неизвестное поле в теле — это `400`, а не «проигнорируем»**: иначе опечатка
  `titel` тихо превращается в заметку без заголовка.
- **Ошибки валидации — `400`, а не `422`.** Делить синтаксис и семантику на пяти
  эндпоинтах — усложнение без выгоды.
- **Ключ идемпотентности хранится в файле, а не в памяти процесса**, и живёт
  24 часа. TTL взят из здравого смысла, ничем не обоснован.
- **Без `Idempotency-Key` повторный `POST` создаёт вторую заметку** — раз клиент
  не попросил защиты от дублей, сервис её не навязывает.
- **`PATCH` на несуществующий `id` — `404`**, запись по чужому id не создаётся.

## Сравнение двух прогонов

Наивный прогон — один промпт «Сделай API для заметок с тегами на Node.js, данные
храни в файле», без спецификации и без правил. Результат лежит в [naive/](naive/)
и не редактировался. Прогон по спеке — всё остальное в этой папке.

Наивный результат — не мусор. Он работает, у него аккуратные комментарии, и одно
решение там лучше, чем в основном прогоне. Разница не в качестве кода, а в том,
что именно осталось нерешённым.

| | Наивный прогон | По спецификации |
|---|---|---|
| Зависимости | Express 5.2.1, 65 пакетов в `node_modules` | ноль |
| Эндпоинты | 8 (`/health`, `/tags`, `GET/POST /notes`, `GET/PUT/PATCH/DELETE /notes/:id`) | 5, как требует задание |
| Автотесты | нет ни одного | 39 |
| Тело ошибки | `{"error": "строка"}` — без кода и без имени поля | `{"error": {"code", "message", "field"}}` |
| Коды | 400, 404, 500 | 400, 404, 405, 409, 500 |
| Границы значений | нет ни одной: заголовок и тег любой длины, `limit` любой | длины строк, число тегов, `limit` 1–100, размер тела |
| `limit=0` | молча вернёт пустой список | `400` с `field: "limit"` |
| Лишнее поле в теле | молча отбрасывается | `400 unknown_field` с именем поля |
| Фильтр по тегам | по умолчанию **ИЛИ**, переключается `?match=all`; неизвестное значение `match` молча трактуется как `any` | всегда **И**, решение записано в спеке |
| Повторный `POST` | создаёт дубль всегда | `Idempotency-Key`: `200` и та же заметка, при другом теле `409` |
| Испорченный файл | сервис стартует, `500` на первом же запросе | сервис не стартует и говорит, какой файл виноват |
| Файл с чужой структурой | молча читается как пустой список, **следующая запись затирает файл** | сервис не стартует, данные не трогает |
| Параллельная запись | очередь записей — гонки нет | очереди не было; добавлена после этого сравнения |
| Неизвестный query-параметр | молча игнорируется | `400` `unknown_field` |

Что из этого важно.

**Совпало без всяких указаний.** Нормализацию тегов наивный прогон сделал ровно
так же — `trim`, нижний регистр, схлопывание дублей, — и даже написал в
комментарии, зачем. То есть спецификация в этом месте ничего не «улучшила».
Ценность спеки была в другом: решение стало явным и проверяемым, а не осталось
частным мнением автора внутри функции.

**Разошлось молча и в противоположную сторону.** Фильтр по нескольким тегам
наивный прогон сделал по ИЛИ. Это ровно та развилка, которую в основном прогоне
выбирал человек, и выбрал наоборот — по И. Ни один тест этого бы не поймал:
поведение не сломано, оно просто другое.

**Потеря данных, которую видно только на границе.** Если файл хранилища
существует, но структура в нём не та, `naive/storage.js:34` возвращает пустой
список — а следующая запись сохраняет этот пустой список поверх файла. Чужие
данные исчезают без единого сообщения. В прогоне по спеке этот случай попал
в контракт до кода, потому что вопрос «что делать с испорченным файлом» стоял
в списке минимальных требований задания.

**Наивный прогон выиграл в одном месте.** В `naive/storage.js:41` записи
выстроены в очередь через промис-цепочку, поэтому два параллельных запроса
не могут перезаписать друг друга. В основном прогоне такой очереди не было: два
одновременных сохранения могли переименовать свои временные файлы в обратном
порядке, и на диск легло бы более старое состояние — в памяти правильное,
в файле нет. Спецификация этот случай не предусмотрела, а наивный агент про
него подумал сам. После сравнения очередь добавлена и покрыта тестом
(20 параллельных созданий, все доезжают до файла).

## Что изменил независимый аудит

Готовый код прочитала другая модель (Sonnet 5) в отдельной сессии, сверяя его
не с тестами, а с `CONTRACT.md`. Четыре находки, все подтвердились:

1. **TTL ключа идемпотентности не проверялся при поиске.** Чистка стояла только
   в записи на диск, а самый частый путь — «тот же ключ, то же тело» — выходил
   из функции раньше записи. Ключ старше суток продолжал работать. Исправлено.
2. **Поле `version` в файле хранилища не проверялось**, и файл без него молча
   перезаписывался уже без этого поля — формат дрейфовал от задокументированного.
   Исправлено.
3. **Файл из одних пробелов** считался пустым и перезаписывался, хотя контракт
   обещал испорченный файл не трогать. Решено в пользу кода — расширена
   формулировка в контракте.
4. **`field` исчезал из тела ошибки**, если именем поля была пустая строка
   (проверка на истинность вместо сравнения с `null`). Исправлено.

Отдельно аудит перечислил семь мест, где контракт молчал, а код принимал
решение сам: лимит тела, потолок `offset`, приоритет ошибок, повторяющиеся
query-параметры и другие. Всё это дописано в контракт. Один пункт из этого
списка привёл к смене поведения: неизвестный query-параметр раньше молча
игнорировался, теперь это `400` — так же строго, как с лишним полем в теле.
