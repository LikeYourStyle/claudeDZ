# Спецификация

Контракт API — эндпоинты, схемы тел, коды ответов, поведение на ошибках —
вынесен в отдельный файл [CONTRACT.md](CONTRACT.md). Он написан до кода и
служит эталоном для аудита: расхождение кода с контрактом считается дефектом
кода, а не поводом переписать контракт.

## Что делаем

Небольшой HTTP-сервис для заметок с тегами. Хранилище — один JSON-файл на диске,
без базы данных и внешних сервисов.

## Для кого и зачем

Учебный проект по курсу: на маленькой поверхности нужно показать полный цикл
работы с агентом — контракт до кода, независимая сверка кода с контрактом, проверка
с доказательством. Пользователь API — условный клиент-приложение, которое
сохраняет заметки и потом ищет их по тегам. Из этого следует одно важное
свойство: клиент мобильный, ретраи по таймауту неизбежны, поэтому создание
заметки должно переживать повторную отправку.

## Сценарии

1. **Создать заметку.** Клиент отправляет заголовок, текст и список тегов.
   Сервер нормализует теги, присваивает `id`, сохраняет в файл и возвращает
   созданную заметку целиком — уже с нормализованными тегами, чтобы клиент видел,
   что сервер с ними сделал.
2. **Найти заметки по тегам.** Клиент запрашивает список с фильтром по одному или
   нескольким тегам. Несколько тегов сужают выборку: возвращаются заметки,
   у которых есть **все** перечисленные теги.
3. **Пролистать список.** Клиент запрашивает список порциями через `limit` и `offset`.
4. **Прочитать одну заметку** по её `id`.
5. **Изменить заметку.** Клиент присылает только те поля, которые меняются.
   Остальные остаются как были.
6. **Удалить заметку.**
7. **Повторная отправка (ретрай).** Клиент не получил ответ по таймауту и
   отправляет тот же запрос на создание ещё раз с тем же `Idempotency-Key`.
   Вторая заметка не создаётся — возвращается та же самая, что и в первый раз.
8. **Клиент ошибся.** Прислал заметку без заголовка, с тегом не той длины,
   с опечаткой в имени поля или с отрицательным `limit`. В ответ — понятная
   ошибка с указанием, какое именно поле не устроило.
9. **Хранилище повреждено.** Файл данных испорчен (не разбирается как JSON).
   Сервер не стартует и говорит, какой файл его не устроил, — вместо того чтобы
   молча затереть чужие данные пустым списком.

## Состояния

| Состояние | Что видит клиент |
|---|---|
| Пусто | `GET /notes` → `200` и `{"items": [], "total": 0, ...}`. Пустая выборка — это не ошибка |
| Есть данные | `200` и список заметок, отсортированный по времени создания, новые сверху |
| Ничего не нашлось по фильтру | `200` и пустой `items`. Отличать «нет заметок вообще» от «нет заметок с такими тегами» на уровне кодов не будем |
| Ошибка клиента | `400` с телом `{"error": {"code", "message", "field"}}` |
| Не найдено | `404` в том же формате: неизвестный `id` или неизвестный маршрут |
| Конфликт | `409`: тот же `Idempotency-Key` прислан с другим телом |
| Хранилище отсутствует | Файл создаётся при первом старте, состояние — пустой список |
| Хранилище пустое (0 байт) | Трактуется как пустой список, файл переписывается корректной структурой |
| Хранилище испорчено | Сервер не поднимается, в консоли — путь к файлу и причина. Данные не трогаются |

## Чего точно не делаем

- Никакой базы данных, Docker и внешних сервисов — это прямое условие задания.
- Никаких внешних npm-зависимостей: только стандартная библиотека Node.
- Нет аутентификации, пользователей и прав доступа. Сервис однопользовательский.
- Нет полнотекстового поиска по заголовку и тексту (`?q=`) — фильтр только по тегам.
  Отброшено сознательно: это ещё один параметр со своей валидацией и своими
  тестами, а поверхность задание требует держать маленькой.
- Нет сортировки по выбору клиента — порядок фиксированный.
- Нет фильтра «хотя бы один из тегов» (OR) и параметра `mode`.
- Нет мягкого удаления и корзины: `DELETE` удаляет насовсем.
- Нет одновременной работы нескольких экземпляров сервиса над одним файлом.
- Нет фронтенда. Проверка — через тесты и файл запросов `requests.http`.

## Допущения

- **Теги нормализуются молча: `trim`, нижний регистр, дубли схлопываются, пустые
  выбрасываются.** Клиенту удобнее, чем ловить `400` из-за лишнего пробела.
  Чтобы нормализация не была невидимой, ответ всегда возвращает итоговый список
  тегов — клиент видит, что сервер изменил.
- **Неизвестное поле в теле — это `400`, а не «проигнорируем».** Опечатка вроде
  `titel` вместо `title` иначе превращается в молча сохранённую заметку без
  заголовка, и клиент узнаёт об этом через неделю.
- **Идемпотентность создания — по заголовку `Idempotency-Key`.** Ключ и `id`
  созданной заметки хранятся в том же файле, а не в памяти процесса: память
  умирает вместе с перезапуском, и весь смысл теряется. Запись о ключе живёт
  24 часа, потом вычищается — иначе файл растёт вечно.
- **Без `Idempotency-Key` повторный `POST` создаёт вторую заметку.** Заголовок
  необязательный: раз клиент не попросил защиты от дублей, сервер её не навязывает.
- **Ошибки валидации — `400`, а не `422`.** Разделять «синтаксис» и «семантику»
  на пяти эндпоинтах — усложнение без выгоды. Единственный `409` — конфликт
  ключа идемпотентности.
- **`PATCH` на несуществующий `id` — `404`.** Создавать запись по чужому id
  сервис не будет: id генерирует сервер.
- **Запись в файл атомарная**: сначала во временный файл, потом переименование.
  Иначе падение посреди записи оставит наполовину записанный JSON — то самое
  «испорченное хранилище», которое мы обещали корректно обрабатывать.
- **Порт по умолчанию 3000**, переопределяется переменной окружения `PORT`.
- **Рантайм — Node.js 22.19.0** (то, что стоит в системе). Тесты — встроенный
  `node:test`, поэтому `npm install` в инструкции запуска нет вообще.

## Открытые вопросы

- Ограничение на длину текста заметки взято на глаз (10 000 символов).
  Если окажется мало — менять придётся и контракт, и тесты.
- TTL ключа идемпотентности в 24 часа ничем не обоснован, кроме здравого смысла.
  Для учебного проекта достаточно, для реального — надо считать по ретраям клиента.
- Не решено, что делать, если файл хранилища вырастет настолько, что перестанет
  помещаться в память. Для учебного объёма (десятки-сотни заметок) неактуально,
  в реальном проекте это первое, что сломается.

## Критерии приёмки

- [ ] Сервис поднимается одной командой из `README.md`, без `npm install`.
- [ ] Реализованы пять эндпоинтов из `CONTRACT.md`, поведение совпадает с описанным.
- [ ] `GET /notes?tags=a,b` возвращает только заметки, у которых есть оба тега.
- [ ] `POST /notes` с тегами `["  Работа ", "работа", "РАБОТА", ""]` возвращает
      заметку с ровно одним тегом `работа`.
- [ ] Повторный `POST` с тем же `Idempotency-Key` и тем же телом возвращает `200`
      и ту же заметку; общее число заметок не увеличивается.
- [ ] Тот же ключ с другим телом возвращает `409`.
- [ ] Неизвестное поле в теле возвращает `400` с именем этого поля в `error.field`.
- [ ] Все ошибки приходят в едином формате, в теле нет ни одной строки стектрейса.
- [ ] Автотесты проходят: минимум один успешный сценарий и минимум три ошибочных.
- [ ] Тесты не ходят в сеть и не пишут в рабочий файл данных — только во временный.
- [ ] Отсутствующий, пустой и испорченный файл хранилища ведут себя так, как
      описано в разделе «Состояния», и это подтверждено тестами.
- [ ] Аудит в чистой сессии не нашёл расхождений между `CONTRACT.md` и кодом
      (либо найденные расхождения разобраны и записаны в журнал).
